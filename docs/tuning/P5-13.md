# P5-13: the AI assumptions

Harness: `tests/unit/Tuning/AiBench.php` (group `tuning`; run `vendor/bin/phpunit -c phpunit.xml.dist --group tuning --filter AiBench`). It calls no AI provider: it builds `Prompts::ideas()` and the largest schema-valid replies from synthetic text, checks each reply with `Schemas::validate()`, and estimates tokens as characters divided by four. Environment: PHP 8.5, unit tests with Brain Monkey.

Every default is kept. The one rule that could have fired (`ai.max_tokens`) has no measured value to move to, so `src/Config.php` is unchanged and every "after" row equals its "before" row. The 1.0-02 addendum at the end of this file supersedes the `ai.max_tokens` result: the limit is now set per request kind.

## ai.max_tokens

Largest schema-valid reply each schema allows, with the sizes assumed in the harness: ideas at `desk.ideas_per_request` (3) with 80-character titles and 240-character angles; a series at `ai.series_max_parts` (12) parts with 80-character titles and six outline lines of 120 characters; and, for context, a typical series of 4 parts with four 60-character lines. Rule: keep unless the largest series reply does not fit, then the smallest measured value that fits.

| Row | reply | estimated tokens | fits 800 | fits 1200 | fits 2000 |
|---|---|---|---|---|---|
| before | ideas (3) | 279 | yes | yes | yes |
| before | series, worst case (12 parts x 6 lines) | 2565 | no | no | no |
| context | series, typical (4 parts x 4 lines) | 393 | yes | yes | yes |

The worst-case series reply does not fit any measured value, so the rule's "smallest measured value that fits" does not exist and the default `1200` is kept (raising it to 2000 would not make the worst case fit). Consequence, recorded for the reviewer: a series proposal near the worst case can be cut off by the token limit. The reply is then not valid JSON, `WpAiClient` returns `masthead_ai_invalid`, and nothing is created (invalid output is rejected, never repaired). Typical requests (up to about 8 parts of 4 lines each) are far below the limit. `ai.max_tokens` is not a settable key, so a site can change it only through the `masthead_config` filter.

| Row | ai.max_tokens |
|---|---|
| before | 1200 |
| after | 1200 (unchanged; no measured value fits the worst case) |

## Addendum 1.0-02: ai.max_tokens per request kind

A single `ai.max_tokens` of 1200 rejected worst-case series proposals, so the limit now depends on the request kind, which is the title of the schema the request uses (`ideas`, `outline`, `share_copy`, `series_proposal`); a plain-text reply or any other schema uses `default`. `ai.max_tokens` in `Config::defaults()` is a map of those five keys. It is still not settable, and a `masthead_config` filter that sets one number applies it to every kind.

Harness: the same `tests/unit/Tuning/AiBench.php` (table 2), extended with the largest outline (12 lines of 120 characters) and the largest share message (600 characters), each validated against its schema. It now also asserts that every kind's configured limit holds its largest reply with the margin below. Estimates are characters divided by four, as before.

Rule: a limit holds a reply when it is at least 1.5 times the estimate, because characters divided by four is rough and JSON punctuation tokenizes worse than prose. Per kind, keep 1200 unless it does not hold the kind's largest reply; then use the smallest measured value (1200, 3000, 4000, 6000) that does. A value at least as large as the estimate but under 1.5 times it is marked "tight".

| Row | kind | largest reply | estimated tokens | needs (x1.5) | 1200 | 3000 | 4000 | 6000 | limit |
|---|---|---|---|---|---|---|---|---|---|
| before | ideas | 3 ideas | 279 | 419 | holds | holds | holds | holds | 1200 |
| before | outline | 12 lines x 120 characters | 373 | 560 | holds | holds | holds | holds | 1200 |
| before | share_copy | 600 characters | 154 | 231 | holds | holds | holds | holds | 1200 |
| before | series_proposal | 12 parts x 6 lines | 2565 | 3848 | no | tight | holds | holds | 1200 |
| context | series_proposal | 4 parts x 4 lines (typical) | 393 | 590 | holds | holds | holds | holds | 1200 |
| after | ideas | 3 ideas | 279 | 419 | holds | | | | 1200 (unchanged) |
| after | outline | 12 lines x 120 characters | 373 | 560 | holds | | | | 1200 (unchanged) |
| after | share_copy | 600 characters | 154 | 231 | holds | | | | 1200 (unchanged) |
| after | series_proposal | 12 parts x 6 lines | 2565 | 3848 | | | holds | | 4000 |
| after | default (plain text) | not used in production | | | | | | | 1200 (unchanged) |

Decision: `series_proposal` 4000 (3000 fits the estimate with only 17% headroom); every other kind keeps 1200. Whether a real provider's tokenizer stays inside 4000 for a 12-part proposal is NOT MEASURED (needs a configured AI provider; human), and the Phase 5 manual check that asks for a 12-part series now checks it.
